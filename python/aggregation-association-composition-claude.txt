You’re right: in code, association and aggregation often look identical. In both, the object is created outside and stored as an attribute.

python
class Doctor:
    def __init__(self, name):
        self.name = name
        self.patient = None      # association

class Team:
    def __init__(self):
        self.players = []        # aggregation
Both hold objects that were created elsewhere. Python can’t tell them apart, so the difference is in the meaning of the relationship.

The real difference: “part of”
Association: two independent objects that know each other. Neither is a part of the other. A Doctor is not a part of a Patient.
Aggregation: a whole made of parts. A Player is a part of a Team.
Aggregation is a special kind of association. It is an association plus the idea that “this is a part of that”. Composition is the same idea with a stricter ownership rule.

Association        →  "A knows B"
  Aggregation      →  "A is made of B (B can live alone)"
    Composition    →  "A is made of B (B dies with A)"
The test
Say it out loud: “X is part of Y.”

“A player is part of a team.” That sounds right, so it’s aggregation.
“A patient is part of a doctor.” That sounds wrong, so it’s association.
“A student is part of a course.” That sounds wrong, since the student just takes the course. It’s association.
Two honest notes
This is a design label, not a code feature. You choose it based on how you describe the real-world relationship. Even many experienced developers say the line between association and aggregation is blurry. In real projects people often just say “association” or “composition”.
A correction to my earlier table: my Teacher.teach(student) example only used the student inside one method. That is a weaker, temporary “uses” relationship. A real association usually stores the other object, like self.patient above.

“Has many” does not mean “is made of”
A Course does hold a list of students, but holding a list is not enough for aggregation. Many associations hold lists too. Aggregation needs the “is part of” meaning, so ask what the whole is made of:

A Team is made of players. Remove all the players and there is no team left.
A Course is made of lessons, modules, and assignments. Students are not its building blocks. They are people who take the course. Remove all the students and the course still exists.
So the course has two kinds of “has many”:

python
class Course:
    def __init__(self, title):
        self.title = title
        # made of -> the course owns these (composition)
        self.lessons = [Lesson("Intro"), Lesson("Loops")]
        # enrolled -> just a link to independent people (association)
        self.students = []

    def enroll(self, student):
        self.students.append(student)
Both attributes are lists. Only the meaning differs, and that is the point.

A useful second test
Ask: “Is the whole defined by these parts?”

A team without players is not a team, so it is aggregation.
A course without students is still a course, so it is association.
Honest note
This is a design judgment. In a school system, some developers might model a class roster as aggregation, and that is not crazy. What matters is that you can defend your choice with a clear reason, and your reasoning on 3 was exactly that kind of thinking.
